# Decisions

Durable execution engine for Elixir, derived from DBOS Transact.

## Standing principle

Stay consistent with the reference implementation. Where the Go engine has made a choice, match it, and record any deliberate departure in the tables below with its reason. A local optimisation that forks the schema, the wire format, or the algorithm costs more than it saves.

## Scope

| Decision | Choice |
|---|---|
| Target languages | Elixir only. Cross-language interop is a non-goal. |
| Reference | `dbos-transact-golang` @ `2a7705c37c93e5fd1d5c1ce049a4224ec2f1f969`, MIT (verified). Vendored read-only at `reference/`, gitignored. |
| Serialization | ETF (`:erlang.term_to_binary/1`), format name `"erl_etf"` in the `serialization` column. One-way door — documented in `docs/interop-migration.md`. |
| System DB | The host application's existing Postgres, via its existing repo and pool. No second pool. |
| Schema | The reference `dbos` schema, unmodified, at migration version 42. |

## Reference facts established in Phase 0

Recorded in `notes/`. Corrections to the original handoff document:

| Claim | Reality |
|---|---|
| 47 migrations | 47 migration *files*, 42 *versions*. Order is a hardcoded Go slice (`system_database.go:427-465`), not filename order. Cockroach and SQLite variants are not on the Postgres path. |
| `setEvent` allocates two step IDs | It allocates **one**. `getEvent` allocates two (`workflow.go:3269-3282`, `3325-3326`). |
| `recovery_attempts` increments unless status is ENQUEUED/DELAYED | Also requires the caller's `IncrementAttempts` flag, set only for dequeue and recovery. |
| `owner_xid` | Written on the INSERT branch only; the ON CONFLICT DO UPDATE never touches it. |
| Admin `/dbos-garbage-collect` | Upstream stub — the route does nothing. The underlying SQL exists. |

## Design

| Decision | Choice | Rationale |
|---|---|---|
| Context passing | Process dictionary, as Ecto threads its transaction. | No second language forces an explicit context argument. |
| Bare workflow call | `Checkout.process_order(id)` is durable. Inside a workflow it becomes a child workflow; outside one it starts a workflow and awaits the result; with the engine not started it raises `Dbos.NotStartedError`. | Ergonomics. The failure mode is loud. |
| Step naming | Function name and arity, module excluded (`"charge_card/2"`). `name:` overrides. | A module move leaves in-flight workflows replayable. |
| Workflow naming | Explicit `name:` required. | Recovery dispatches on it. |
| Determinism | Compile-time checker over the `defworkflow` body AST. | Step inputs are not stored, so the runtime `function_name` check cannot catch argument drift. |
| Errors | The raised exception struct, ETF-encoded, re-raised on replay with its type intact. | |
| Reserved step names | Reuse the upstream `DBOS.*` strings verbatim. | The DBOS console renders our workflows for free. |
| Transactional steps | `sameAsSystemDB` single-transaction path first. Separate-database Layer 2 only on demand. | The common Elixir deployment shares one database. |
| Migrations | Verify at launch, refuse to start on mismatch. Opt-in creation for dev. | |
| Workflow processes | `DynamicSupervisor` children, `:temporary`. | An OTP restart would re-invoke the body outside the replay path. |

## Phase 1

| Decision | Choice | Rationale |
|---|---|---|
| Serialization column encoding | `Dbos.Serialization.encode/1` is `:erlang.term_to_binary/1` then `Base.encode64/1`; `decode/1` reverses it. | Mirrors the reference's own gob serializer, which base64-wraps binary output into the same TEXT column (`dbos/serialization.go:150`). The columns are an opaque, format-agnostic payload slot — the `serialization` column exists so several encodings can coexist — and upstream base64-wraps even its default JSON serializer (`serialization.go:92`). JSONB was considered and rejected: it would forfeit the pluggable-format design, the DBOS console, and schema fidelity. |
| `nil` round-trip | No sentinel marker (unlike upstream's `"__DBOS_NIL"` string for `DBOS_JSON`). `nil` is a native ETF term and round-trips through `encode/1`/`decode/1` like any other value. | ETF, unlike JSON-over-a-string-column, has no ambiguity between "absent" and "the value nil" to work around. |
| Decoding unsafe terms | `decode/1` uses `:erlang.binary_to_term(binary, [:safe])` and additionally walks the result rejecting any pid, port, or reference, raising `ArgumentError`. | `:safe` alone does not reject pids/ports/refs already present in the source binary (verified empirically) — only atom-table growth. Workflow inputs/outputs are not process identities and should never contain one. |

## Phase 2b

| Decision | Choice | Rationale |
|---|---|---|
| Engine namespacing | Every per-engine process (`Dbos.Registry`, `Dbos.WorkflowSup`, its `DynamicSupervisor`, the process-tracking `Registry`, `Dbos.Recovery`) is named via `Module.concat(engine_name, ThatModule)`, and the resolved `Dbos.Config` lives in `:persistent_term` keyed by `{Dbos, :config, engine_name}`. | Lets multiple engines coexist in one BEAM with no global singletons or unnamespaced atoms, per the task's two-node test requirement. |
| `executor_id` default | `System.get_env("DBOS__VMID")`, else `to_string(node())`. | Deviates from upstream's literal `"local"` fallback (`notes/recovery.md` §2) by substituting the BEAM node name, as directed — a more useful default in a clustered Elixir deployment, and still non-empty (upstream's `ListWorkflows{ExecutorIDs: [...]}` gotcha about a real, non-empty value still holds). |
| `application_version` default | `System.get_env("DBOS__APPVERSION")`, else `Dbos.Version.compute/1` over the registered workflow modules' BEAM code chunks (SHA-256 over every chunk except `Docs`, truncated to 16 hex chars). | Upstream hashes the whole compiled executable (`getBinaryHash`, `dbos.go:940-973`), which has no equivalent in a BEAM release (no single "the executable"); hashing the registered workflow modules' own code is the closest equivalent that is still deterministic across runs of the same code and changes when workflow code changes. |
| Migration verification | Runs as a plain function call inside `Dbos.Supervisor.init/1` (raising aborts the supervisor start), not as a supervised child. | Functionally equivalent ordering guarantee to a dedicated child (it still runs after `Dbos.Registry` starts and before `Dbos.WorkflowSup`/`Dbos.Recovery`), without an awkward one-shot child spec. |
| `dbos_schema.sql` statement splitting | `Dbos.Migrator.create!/1` reads the fixture and splits it into individual statements with a small state-machine splitter (tracking `$$...$$` dollar-quoted bodies and `--` line comments) rather than executing the file as one multi-statement string. | Postgrex/Ecto's extended query protocol does not support multiple SQL commands in one prepared statement; the fixture also mixes `CREATE INDEX CONCURRENTLY` (illegal inside a transaction block) with trigger functions containing embedded semicolons, so each statement must run as its own top-level query. |
| Recovery's `max_retries` | `Dbos.Config.max_recovery_attempts`, default `3`, threaded into `insert_workflow_status(..., max_retries: config.max_recovery_attempts)` on every recovery re-dispatch. | Upstream's `MaxRetries` is a per-workflow value not persisted in `workflow_status` at all (only ever a caller-supplied parameter to `InsertWorkflowStatus`); since Phase 2b has no per-workflow options surface yet, recovery needs *some* value to drive the `MAX_RECOVERY_ATTEMPTS_EXCEEDED` transition. An engine-level default stands in until a later phase threads a real per-workflow value through. **Flagged for review** — this is invented, not specified by the reference. |
| Recovery-at-boot vs. a fresh `Dbos.start` | Recovery's initial scan runs in `handle_continue` (per the task), which is not guaranteed to complete before `Dbos.Supervisor.start_link/1` returns to the caller. A workflow started immediately after boot could theoretically race the boot-time recovery scan if (implausibly) a same-ID workflow were already `PENDING`; in practice this only matters for genuinely pre-existing `PENDING` rows, and `Dbos.Recovery.await_boot_recovery/1` (`:sys.get_state/1` on the recovery process) is exposed so tests can serialize against it deterministically. | Accepted trade-off, per the task's explicit "must not block `start_link`" requirement; documented rather than silently working around it. |
| Child workflow start point | `Dbos.start/3`, called from inside a workflow, detects the ambient context via `Dbos.Runtime.in_workflow?/0` and reads its `Dbos.Config`/engine from `Dbos.Runtime.current_config/0` rather than from the caller's `opts[:engine]`. | A workflow body calling `Dbos.start` for a child should always target the same engine it is itself running under; requiring the body to know and repeat its own engine name would be redundant and error-prone. **Invented** — the reference has no concept of a separate "engine" to disambiguate, so there is no equivalent upstream behavior to match against. |
| Workflow process failure handling | `Dbos.WorkflowProcess` classifies a rescued/caught failure by matching `%Dbos.WorkflowCancelledError{}` specifically (kind `:error`) and skips calling `update_workflow_outcome` entirely in that case, rather than calling it and relying on its own cancellation guard. `update_workflow_outcome`'s own `WorkflowCancelledError` (raised if the row was cancelled concurrently, underneath the call) is also rescued and treated as `:ok`. | Belt-and-suspenders: covers both "the body itself observed cancellation and raised" and "cancellation landed in the gap between the body finishing and the outcome write," per `notes/engine-core.md` §5. |

## Phase 3b: dead-executor recovery

The reference has no executor heartbeat and no liveness table. `recoverPendingWorkflows(ctx, executorIDs)` takes a list of executor ids, boot calls it with its own, and `POST /dbos-workflow-recovery` lets an operator name any others. Deciding who is dead belongs to the Conductor control plane, which is out of scope. The BEAM already knows when a node dies, so this port closes the gap itself, entirely with built-in OTP (`:pg`, `:net_kernel`), no clustering library. Documented in full in `docs/clustering.md`.

| Decision | Choice | Rationale |
|---|---|---|
| Reclaim primitive | `Dbos.Recovery.reclaim/2,3` takes a list of executor ids, matching upstream's signature. `recover_pending/1` is the special case of "my own id", with an unbounded batch so its behaviour is unchanged from before `reclaim` existed. | Restores the upstream primitive Phase 2b had narrowed to this executor's own id. |
| Node to executor mapping | One shared, deployment-wide `:pg` group (`Dbos.Cluster`, default name `Dbos.Cluster.Group`, configurable), not a group scoped to one engine's name. Every member publishes `{node, executor_id}`, cached locally by every engine and refreshed on join. Nothing persisted. | One BEAM node can host several engines with distinct executor ids, so the mapping is many-to-one; each engine needs the whole roster, not only its own engine name's slice of it. |
| Node departure vs. live roster | `Dbos.Cluster` tracks two things: a live `members` map (mutated on `:pg` join/leave, backing `roster/1`) and a separate, monotonic `seen_by_node` history that is only ever added to, backing `executor_ids_for_node/2`. | A `:pg` leave notification and `:net_kernel`'s own `:nodedown` notification for the same node race with no ordering guarantee. Resolving a departed node's executor ids from a live-only map risks reading it after `:pg`'s own cleanup already ran, silently skipping the reclaim; the monotonic history is unaffected by that race, at the cost of never forgetting an executor id once seen (acceptable — the set is bounded by every executor a deployment has ever run). |
| Detection | `Dbos.Cluster.NodeWatcher`: `:net_kernel.monitor_nodes(true)`, behind an opt-in flag. Reclaim on `:nodedown` runs in an unsupervised `Task`. | Immediate and exact. A heartbeat table is slower, chattier, and equally wrong when a node pauses. The engine must never require distributed Erlang, and a slow reclaim pass must never block node-down handling. |
| Orphan sweep | `Dbos.Cluster.OrphanSweep`: periodic scan for `PENDING` rows whose `executor_id` is absent from the live roster and whose `updated_at` exceeds a conservative threshold (default 5 minutes for both the interval and the threshold). Off by default, and only meaningful with `cluster.enabled`. | Covers executors no live node ever saw depart: a whole-cluster restart, or a pod that is permanently gone. The only piece needing a time heuristic, so it stays a slow safety net. Once an executor id is flagged stale, every one of its `PENDING` rows is reclaimed together, not only the individually-stale ones — the absence from the roster is the real signal; age just avoids flagging an executor that simply hasn't joined the roster yet. |
| Choosing the survivor | No election. Every survivor may run `UPDATE workflow_status SET executor_id = $me WHERE executor_id = ANY($dead) AND status = 'PENDING' AND queue_name IS NULL AND workflow_uuid IN (SELECT ... ORDER BY created_at ASC LIMIT $batch FOR UPDATE SKIP LOCKED) RETURNING ...` and redispatches only the rows its own statement returned. | The `UPDATE` is the serialization point, so the database decides atomically. `FOR UPDATE SKIP LOCKED` lets concurrent callers claim disjoint batches without blocking each other, the same pattern already used by `dequeue_candidate_ids/4`. |
| Application version filter | The reclaiming `UPDATE` also filters `application_version = config.application_version` when set, exactly like `ListWorkflows`, for both own-id and dead-id reclaim. | An executor can only usefully re-run code matching its own registered version, regardless of whose id it is reclaiming. |
| Queued workflows | Excluded from the reclaiming `UPDATE` (`queue_name IS NULL`). A separate query finds queued `PENDING` rows owned by the dead ids and clears each back to `ENQUEUED` via the existing `clear_queue_assignment/2`. | The queue already balances work; reassigning `executor_id` on a row about to go back to `ENQUEUED` would be immediately overwritten by the next dequeue anyway. |
| Batch size default asymmetry | `reclaim/2` with no `:batch_size` opt is unbounded (`recover_pending/1`'s historical behaviour); `Dbos.Config.reclaim_batch_size` (default `50`) is what `NodeWatcher`/`OrphanSweep` pass explicitly. | Preserves "no existing test changes meaning" for `recover_pending/1` while still giving cluster-driven reclaim a sensible, configurable batch size, per the task's explicit requirement for both. |
| Peer-node testing | `test/dbos/cluster_peer_test.exs` uses `:peer.start_link/1` (with `-pa` args so the peer node loads this project's own compiled modules) to genuinely exercise `Dbos.Cluster`/`NodeWatcher` against a second connected node, including a real `:nodedown`. Tagged `:integration` (excluded by default) since it starts distributed Erlang for the whole test run. | `GenServer.start_link/3` run via `:erpc.call/4` links the new process to `:erpc`'s transient per-call worker, which was killing the remote `Dbos.Cluster` process moments after every remote start; `GenServer.start/3` (unlinked) avoids it. |

Accepted risk: under a network partition each side sees the other as dead and both reclaim, so a step body can run twice on two live nodes. `owner_xid` detects this after the fact. A quorum would trade it for refusing to recover during a partition, which is its own outage.

## Deviations and invented behavior needing review

- `max_recovery_attempts` as an engine-level `Dbos.Config` field (see Phase 2b table above) — the reference has no equivalent single knob; a later phase should replace this with whatever per-workflow retry configuration surface it introduces.
- The exact wording and log level (`Logger.warning/1`) of recovery's "unregistered workflow name" and "dead-lettered during recovery" messages are invented; upstream logs similarly but the message text is not part of any documented contract.
- `Dbos.Registry.name_for_mfa/2` (reverse lookup, name for a given `{module, function, arity}`) is new surface not requested verbatim by the task, added because resolving a capture (`&Mod.fun/n`) passed to `Dbos.start/3` requires it.
- `Dbos.WorkflowSup.whereis/2` (workflow id → pid) is new surface, added because the crash-and-resume acceptance test needs a way to locate a running workflow's process to kill it; the task only asked for the queue/partition-key live count.
- `Dbos.Cluster.OrphanSweep`'s reclaim-the-whole-executor-once-any-row-is-stale behavior (see Phase 3b table above) is invented; upstream has no orphan sweep at all to match against.
- `Dbos.Config.cluster_group` (default `Dbos.Cluster.Group`) is new surface: nothing upstream needed a shared cluster identity, since it has no `:pg`-based roster at all.

## Phase 5: cancel, resume, fork, timeouts, garbage collection, transactional steps

| Decision | Choice | Rationale |
|---|---|---|
| Stopping a cancelled workflow's live process | Cooperative, not a hard kill. A workflow running plain steps stops at its next `check_operation_execution` call (already raised `Dbos.WorkflowCancelledError` before this phase). A workflow blocked in `recv`/`get_event`/a durable `sleep` is woken immediately: `Dbos.cancel/2` looks up the live pid via `Dbos.WorkflowSup.whereis/2` and sends it `{:dbos_notify, :cancelled, workflow_id}` — the exact message shape `Dbos.Notifications.wait_until/3`'s `receive` already matches, so no new message protocol was needed. Every wait site's `recheck_fun` now also checks `Dbos.SystemDb.workflow_cancelled?/2`, and raises `Dbos.WorkflowCancelledError` right after waking. | The BEAM has no context-cancellation equivalent to Go's `context.AfterFunc`, but it does have arbitrary process messaging into an already-blocked `receive`; reusing the existing wake channel avoids inventing a second one, and stopping cooperatively (never `Process.exit/2`) keeps the "the row is already durably CANCELLED before anything about the process is touched" invariant simple. |
| Durable `sleep` interruptibility | Replaced the plain `Process.sleep/1` in `Dbos.Messaging.sleep/2` with the same `Dbos.Notifications.wait_until/3` wake loop `recv`/`get_event` use. | `Process.sleep/1` cannot be interrupted by a message; a durable sleep must be cancellable promptly, per the task's explicit requirement. |
| Timeout/deadline enforcement | Per-workflow, process-local, like upstream — but as an unsupervised timer `Task` (`Dbos.Runtime.arm_deadline/2`, started once per workflow process right before its body runs) that sleeps until the deadline then calls `Dbos.cancel/2`; harmless no-op if the workflow already finished. | No BEAM equivalent to `context.AfterFunc`; a lone timer task is the simplest analogue and costs one extra lightweight process per running workflow, only while it is actually running. |
| Child deadline inheritance | A child workflow's `workflow_deadline_epoch_ms` is set directly, at insert time, from `Dbos.Runtime.current_deadline_epoch_ms/0` — the parent's own already-armed absolute deadline, if any — rather than recomputing a fresh timeout. No override option is exposed for children. | Matches the Go reference exactly (`workflow.go:1312-1328`): a child call reads `c.Deadline()` off the *parent's* ambient context, which already carries `WithTimeout` from the parent's own deadline; there is no separate per-child timeout knob in that code path either. |
| Internal queue always has a live runner | `Dbos.Queue.Sup` now always starts a `Dbos.Queue.Runner` for `Dbos.Queue.internal_queue_name/0`, in addition to any declared `:queues`, constructing the `%Dbos.Queue{}` directly to bypass `Queue.new/2`'s reserved-name guard. | `Dbos.resume/2` and `Dbos.fork/3` re-enqueue onto the internal queue by default, matching upstream's `InternalQueueName` default — but nothing before Phase 5 ever started a runner for it, so a resumed/forked workflow would sit `ENQUEUED` forever. Upstream always has this runner running; this closes that gap rather than inventing new behavior. |
| Cancel's `CancelChildren` option | Not implemented. `Dbos.cancel/2` cancels exactly the given id. | Out of scope for the acceptance tests; the BFS-over-`GetWorkflowChildren` expansion upstream does is a straightforward addition for a later phase, flagged here rather than half-implemented. |
| Transactional steps: which path | Only the `sameAsSystemDB` single-transaction path (`DECISIONS.md`'s existing Phase 0 row). `Dbos.Config` has exactly one `conn`/pool for both the system database and the user's own data — there is no second-database configuration surface at all — so the separate-database three-layer protocol (`transaction_completion` table, Layer 1/Layer 2 replay) has nothing to attach to and was not built. | The system DB is always the host application's own Postgres via its own repo/pool (Phase 0 scope decision); implementing a `transaction_completion`-table protocol with no way to ever configure a second database would be dead code. |
| Transaction failure checkpointing | A transactional step that raises records nothing at all (no `operation_outputs` row, success or failure) — the whole `config.db.transaction/3` call rolls back, including any attempted checkpoint write, and the exception simply propagates. | Because Layer 1 and the user write commit in one transaction in this path, "nothing committed" is the only state a failed attempt can leave; a fresh replay attempt executing the body again is exactly correct, not a gap needing a recorded failure to protect against. |
| Step-in-transaction guard | Added an explicit runtime check (`Dbos.StepInTransactionError`) in `Dbos.Runtime.run_step_at/4`, since every durable primitive (`send_message`, `recv_message`, `set_event`, etc.) funnels through it. | Upstream prevents this at compile time via `Txn[R]`'s plain-`context.Context` function signature; this port has no type-level equivalent, so `notes/datasource.md` §5/§7 calls for an explicit runtime guard — a deliberate addition, not upstream behavior. |
| `Dbos.SystemDb.get_workflow_result/2` | Now returns `{:error, %Dbos.WorkflowCancelledError{}}` and `{:error, %Dbos.MaxRecoveryAttemptsExceededError{}}` distinctly instead of collapsing both into `:pending`. `Dbos.await/2` already distinguished them (unchanged). | Fixes the Phase 1 placeholder now that cancellation is real, per the task. |
| Resuming an already-terminal workflow | `Dbos.resume/2` on a `SUCCESS`/`ERROR` workflow is a silent no-op — the row is left completely unchanged (matches `ResumeWorkflows`'s `WHERE status NOT IN (SUCCESS, ERROR)` guard, which still reports the id as "existing"). | Matches upstream exactly; there is no error path for this case to preserve. |
| Workflow-process registration race | `Dbos.WorkflowSup.start_workflow/5` now blocks (bounded at 1s) until the newly started `Dbos.WorkflowProcess` acks that it has registered itself in the process-tracking `Registry`, via a `caller: self()` handshake. | Pre-existing race, unrelated to Phase 5's own scope, but Phase 5's cancel/timeout paths call `Dbos.WorkflowSup.whereis/2` immediately after starting workflows in several new tests, and the added system-wide scheduler pressure from the internal queue runner surfaced the race as an intermittent `workflow_sup_test.exs` failure; fixed rather than left flaky. |
